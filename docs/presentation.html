Register users/agents, approve or suspend agents, block wallets, audit all transactions, manage fees and commission.

SecurityToken scoping with Sanctum abilities

Every protected route checks two things

  • Does the user hold the required role?
  • Does the token carry the matching ability?

Why it matters

If someone brute-forces a short PIN and logs in on the user route, that token carries only user. It can never call admin endpoints — the admin password and OTP stay meaningful.

In code: route groups like auth:sanctum + ability:user + password.changed. Forced password change is enforced by middleware, not per-controller checks.

Credential lifecycleGranting access and recovering PINs

Admin wants agent/user access

Requests OTP by email → submits OTP + new PIN. Setting a PIN grants a credential, not a role.

User wants admin access

Admin assigns email + temporary password, issues a one-time signed URL. User accepts invite and must change password first.

PIN reset (staff-initiated)

Users can't self-reset. Customer care verifies identity out-of-band, submits phone + email, and a signed link lets the user choose their own PIN. Staff never see it.

Admin password reset is separate and self-service via email OTP.

WalletsOne wallet per user

  • Created automatically at registration with a BDT 50.00 starting balance.
  • Admins can block / unblock wallets (recorded with reason and actor in audit logs).
  • Blocked wallets can neither send nor receive — checked in the service layer before any financial operation.
  • Balances are DECIMAL, handled with string math (bcmath), never floats.

Financial integritySafe under concurrency

1 · IdempotencyLook up key per initiator; replay returns the original result
→
2 · DB::transactionAll-or-nothing
→
3 · Lock caps rowlockForUpdate()
→
4 · Lock walletsOrdered by user_id
→
5 · Check & applyBlocked? Balance? Caps? Then write txn
  • Row locking stops two simultaneous requests from spending the same balance (double spend).
  • Deterministic lock order (Cap → Wallets sorted by id) prevents deadlocks.
  • Idempotency keys scoped to the initiator make retries safe and prevent key leakage across users; a unique constraint is the backstop for races.
  • Failure at any step rolls back everything — no partial balance changes.

Fees · commission · capsWhere the money rules live

Fee

FeeCalculator reads system_fee_rate from settings; computed with bcmul, rounded to 2 decimals.

Commission

CommissionCalculator uses the agent’s own rate or the default 1%; capped by the fee. Paid as a separate COMMISSION_PAYOUT transaction.

Caps

CapService enforces daily and monthly limits per user, checked inside the same DB transaction as the balance change.

Scheduled jobs ResetDailyCaps (00:00 UTC daily) and ResetMonthlyCaps (1st of month) zero usage. All times are stored in UTC; the frontend localizes.

AuditabilityEverything is traceable

  • Transactions record who initiated, all parties, amounts, fee and commission rates, and balances after.
  • Agent approval stores approver and timestamp.
  • Wallet block/unblock, settings changes, and PIN-reset initiation are written to audit_logs.
  • Financial records are not casually deleted.

SummaryDesign principles

Separation

HTTP layer, domain services and persistence are kept apart in modules.

Least privilege

Role + token ability on every route; PIN tokens never act as admin.

Money-safe

Transactions, row locks, ordered locking, idempotency, decimal math.

Auditable

Immutable rates and balances-after on every record, plus audit logs.
